# CLAUDE.md

Taxinha is a cross-platform (Windows/macOS/Linux) sticky-notes desktop app built on **Tauri 2**. Each note is its own frameless window; the headline feature is the pin button, which toggles "always on top". Comments and commit-facing docs are in **Brazilian Portuguese** — keep new code consistent with that. The UI is translated: Portuguese (default) and English (see *Languages* below); every new user-facing string needs both.

## Commands

```bash
npm install
npm run dev      # tauri dev — runs the app with the Rust backend in debug (also "Rodar em modo dev" in .vscode/launch.json)
npm run build    # tauri build — installers in src-tauri/target/release/bundle/
```

Windows installer without a local toolchain: `docker compose -f docker/compose.yml run --build --rm windows` (also the "Gerar instalador do Windows (Docker)" entry in `.vscode/launch.json`). It cross-compiles with `cargo-xwin` and outputs only the NSIS `*-setup.exe` to `dist/` (no `.msi` — WiX needs Windows). `node_modules`, `target` and caches live in Docker volumes, separate from the host's.

There are no tests, linters or JS build step. For Rust-only checks: `cargo check` / `cargo clippy` inside `src-tauri/`.

CI (`.github/workflows/build.yml`) builds installers for Windows, macOS arm64 + x64, and Linux (ubuntu-22.04). It runs only via `workflow_dispatch` (manual); run from a `v*` tag, it creates a draft GitHub release via `tauri-action`. Builds are unsigned.

## Layout

```
src/                 frontend — plain HTML/CSS/JS, no bundler, served as-is (frontendDist = ../src)
  index.html         markup for ONE note window (titlebar, colour popover, format bar, editor, statusbar)
  app.js             per-window logic; talks to Rust via window.__TAURI__ (withGlobalTauri)
  base.css           shared by both pages: fonts, tokens, light/dark themes, label colours, swatches,
                     and the window chrome (.frame, .titlebar, .icon-btn, .pin, .collapse, .grip)
  i18n.js            UI strings pt/en (`TaxinhaI18n.t`), placeholder phrases, data-i18n helpers
  chrome.js          shared window behaviour: titlebar drag and edge/corner resize, both with snapping; double/middle click
  styles.css         note window components, derived from docs/style.md
  manager.html/.js/.css  the "Gerenciador" window: tabs Notas / Lixeira (with search) / Configuração
  fonts/             bundled Inter woff files (CSP forbids remote fonts)
src-tauri/
  src/main.rs        window creation, Tauri commands, tray menu, app lifecycle
  src/store.rs       Note model + persistence to notes.json
  src/welcome.rs     welcome note created on first run (title, HTML + matching plain text)
  tauri.conf.json    app id br.taxinha.notas, CSP, bundle config (no static windows)
  capabilities/default.json  permissions for windows labelled note-*
  icons/             generated from assets/icon.svg; tray.png / tray-template.png (macOS)
docs/style.md        design reference ("Linear"-style dark system) the UI follows
```

## Architecture

**One window per note.** Window label is `note-{id}`; Rust derives the note id from the calling window's label (`id_of`), so commands never take an id argument — the frontend just calls `invoke('save_text', { text })` etc. and it applies to its own note. All windows load the same `index.html`; `app.js` calls `load_note` on startup to get its data.

**Rust is the source of truth.** `Store` (`store.rs`) holds all notes in a `Mutex<FileData>` and sets a `dirty` flag on change. A background thread calls `flush()` every 800 ms; it writes atomically (`notes.json.tmp` → rename). Unreadable `notes.json` is backed up as `notes.corrompido-<ms>.json` before starting fresh — never overwrite user data. `flush()` is also called explicitly on delete, quit and `RunEvent::Exit`.

**Tauri commands** (`main.rs`, registered in `generate_handler!`): note windows use `get_theme`, `drag_to`, `resize_to`, `load_note`, `save_text`, `set_pinned`, `set_color`, `set_collapsed`, `set_title`, `new_note`, `trash_note`; the "Gerenciador" window uses `load_manager`, `close_manager`, `list_notes` (all notes, `html` stripped), `open_note`, `move_to_trash`, `restore_note`, `delete_forever`, `empty_trash`, `get_default_color`, `set_default_color` — these take explicit note ids. Commands that create/destroy windows are `async` on purpose — creating/destroying windows from sync commands can deadlock on Windows. When adding a command, register it in `generate_handler!`; if it needs a new window API from JS, add the permission in `capabilities/default.json`.

**Geometry** is tracked from `WindowEvent::Moved/Resized` in `track_geometry`. Position is stored in *physical* pixels, size in *logical* pixels. `height` always stores the expanded height; while collapsed the window is `COLLAPSED_H` (36px, matches `--titlebar-h` in CSS). Saved positions are only restored if the titlebar would be on a connected monitor (`is_on_screen`); Windows' `-32000` minimise coordinates are ignored. Dragging is done by the page, not `startDragging`: the titlebar captures the pointer, sends `origin + delta × scale` to the `drag_to` command at most one call in flight (latest position wins, the final one is always sent), and `drag_to` applies `snapped` before `set_position`. `snapped` collects candidate corner positions per axis — the work-area edges of the monitor under the note's centre, plus the edges of every other visible note in the same row (for x) or column (for y): side by side with a uniform `SNAP_GAP` (6 logical px) between them, or aligned — and picks the nearest one within `SNAP_DISTANCE` (16 logical px). All snapping uses the visible rect (`inner_position`/`inner_size`), not the outer one: on Windows an undecorated window has an invisible 8 px resize border on the left, right and bottom (not the top), which would leave uneven gaps; `drag_to` converts between the two with the inner−outer offset. The native drag loop can't do this because the OS owns the window until the button is released. Resizing works the same way: windows are built with `resizable(false)`, `chrome.js` adds invisible handles on the 4 edges and 4 corners (plus the visible bottom-right grip; only left/right while collapsed) and sends the requested visible rect to `resize_to`, which snaps only the moving edges using the same `SnapTargets` (per-edge candidate lines shared with `snapped`) and enforces `MIN_W`/`MANAGER_MIN_W` × `COLLAPSED_H`. A note created with `+` is placed by `beside`: next to its parent with the same visible `SNAP_GAP` (computed on inner rects, assuming the new window has the parent's invisible borders), right side first, else left, within the monitor work area; if another visible note already sits on that spot, it steps down by `COLLAPSED_H + 8` until free, so repeated `+` clicks cascade instead of stacking.

**Trash:** the ✕ button / middle click (`trash_note`) and the manager (`move_to_trash`) both go through `trash()`, which sets `trashedAt` and destroys the window (a note with no text and no title is removed outright). Only notes with `trashedAt == None` (`Store::active`) are opened at startup. Notes older than `TRASH_TTL_MS` (30 days) are purged on load and hourly by the saver thread. Permanent deletion only happens from the trash (manager) or by that purge.

**Manager ("Gerenciador" window):** label `manager` (`MANAGER`), page `manager.html`. It behaves like a note — frameless, same titlebar (pin, +, collapse, ✕), drag with snapping and middle-click close via `chrome.js`, resize grip, its position/size/pinned/collapsed persisted in `FileData.manager` (`ManagerState`) — but has a fixed "Gerenciador" title, no editor and no colour dot. `set_pinned`/`set_collapsed`/`track_geometry` branch on `is_note` to update the manager state instead of a note; ✕/middle click call `close_manager` (no trash). Notes snap to it and `+` from it opens a note beside it. Opened by `open_manager` at startup / relaunch and from the tray item "Gerenciador" — notes have no button for it. The tray no longer manages notes. Every change to the note list emits `notes-changed` (`notify`), and the manager reloads `list_notes` on it (debounced). It also sets the default colour for new notes (`FileData.default_color`, used by `Store::create`). Helpers that iterate note windows (`show_all`, snapping, `beside`) must use `note_windows`/`is_note` so the manager window is ignored. The tray menu has only static items (Nova nota, Mostrar todas as notas, separator, Gerenciador, separator, Sair da Taxinha); theme and "Como usar a Taxinha" (`show_welcome`) live in the manager's "Configuração" tab. The manager has three tabs — Notas and Lixeira (both with the search box) and Configuração (theme; colour, title and text for new notes; help, quit; no list, no search). New-note defaults live in `FileData` (`default_color`, `default_title`, `default_text` — plain text, `[ ] ` lines become checklist items via `fromPlain` since the new note's `html` is empty) and are applied in `Store::create`; `trash()` deletes outright a note still equal to those defaults (`Store::is_pristine`).

**Theme:** app-wide setting stored in `notes.json` (`FileData.theme`: `system` | `light` | `dark`, empty = system), chosen in the manager's segmented switch (`change_theme` command). `set_theme` saves it, updates every window's native background (`apply_background`: `PAPER` or `CARBON`; "system" uses `window.theme()`, re-applied on `WindowEvent::ThemeChanged`) and emits `theme-changed`; `app.js` reads it with `get_theme` and sets `<html data-theme>` (no attribute = follow the OS through `prefers-color-scheme`). In CSS the light theme redefines the same grey tokens (`--color-carbon`, `--color-mist`, …) plus the `--overlay-*`, `--selection` and `--shadow-popover` tokens — never use raw white/black overlays, use those tokens so both themes work.

**Startup:** the Gerenciador opens on every launch (`setup`), on relaunch through the single-instance plugin and on macOS Dock reopen, together with the notes that were open. **First run:** when `Store::is_first_run()` (no notes and `next_seq <= 1`, i.e. a fresh `notes.json`), `setup` creates the welcome note from `welcome.rs` instead of an empty one, placed beside the Gerenciador (`open_welcome(app, pos)` with `beside`). The manager's "Como usar a Taxinha" button (`show_welcome`) reopens it through the same `open_welcome`, which focuses an untouched copy (same title and HTML) if one is open instead of duplicating it. Its `HTML` must only use tags the `sanitize` whitelist keeps, and `TEXT` must equal what `toPlain` produces from that HTML.

**Languages:** `FileData.language` is `system` | `pt-BR` | `en` (empty = system); `Store::effective_language()` resolves it to `"pt"` or `"en"` (system: `sys-locale`, Portuguese for any `pt*` locale, English otherwise). Pages call `get_language` → `(setting, effective)` and `TaxinhaI18n.set(effective)`; the manager's Configuração has a language list (`<select id="languageSelect">`, `change_language`), and `set_language` emits `language-changed` (effective lang) to every window, rebuilds the tray (`refresh_tray`, main thread) and retitles the manager. In HTML, static text uses `data-i18n="key"` and `data-i18n-attr="attr=key,…"`; JS uses `t('key', vars)`. Rust-side strings (tray labels, manager window title, welcome note) are chosen with the effective language (`tray_labels`, `manager_title`, `welcome::for_lang`). Note content and new-note defaults are never translated.

**Lifecycle:** single-instance plugin (relaunch → `show_all`). Each note window appears in the taskbar (grouped under the app icon); on macOS the app has a Dock icon and `RunEvent::Reopen` → `show_all`. Closing the last window doesn't quit (`prevent_exit` when no exit code); with no notes open the app lives only in the tray, and only "Sair da Taxinha" (tray menu, or `quit_app` in the manager's Configuração tab) exits. On Linux under Wayland, `GDK_BACKEND=x11` is forced (unless already set) so always-on-top works through XWayland.

**Frontend (`app.js`)**: a single IIFE. Text saves are debounced 250 ms and flushed on blur/window blur/beforeunload. Pin toggling is optimistic and reverts on error. Titlebar layout: pin on the far left, colour dot (`#colorBtn`, opens the swatch popover `#colorMenu`), name, then new / collapse / close on the right. It handles drag (custom, see below), middle-click close (`auxclick` → `closeNote`, same as ✕) and double-click rename (inline `#titleInput` → `set_title`, max 80 chars). All titlebar buttons stay visible when collapsed; opening the colour popover on a collapsed note grows the window (`setSize`, not persisted since `height` is only tracked while expanded) and shrinks it back when the popover closes or the window loses focus. The note name (or first line) is mirrored to the native window title (`setTitle`) for the taskbar. The bottom-right grip calls `startResizeDragging`.

**Editor:** `#editor` is a `contenteditable` div; each line is a `<div>`, formatting is `<b>`/`<i>`/`<u>` (`styleWithCSS` off) plus text size as `<font size="2|3|5">` from `execCommand('fontSize')` (`SIZES` in app.js; real px sizes in the `.editor font[size]` CSS rules — keep the two in sync), and a checklist item is `<div class="check">` (checked: `check done`, box drawn in CSS `::before`). The note stores both `html` (the editor's `innerHTML`, re-sanitised to that whitelist on load by `sanitize`) and `text` (plain text via `toPlain`, items as `[ ] ` / `[x] `) — Rust only reads `text` (`is_blank`), and notes with empty `html` are rebuilt from `text` (`fromPlain`). `save_text` takes both. Typing `[]` at line start turns the line into an item, clicking the box toggles it, Enter on an item continues the list (the browser clones the block; `done` is cleared), Enter on an empty item or Backspace at its start leaves the list. Paste is always plain text. Formatting: Mod+B/I/U, Mod+Shift+> / Mod+Shift+< (text size, matched by `e.code` Period/Comma), or the floating `#formatBar` (N / I / S + three "A" size buttons) shown above a non-empty selection — hidden while the mouse drags a selection, repositioned on `selectionchange`/scroll/resize, buttons use `mousedown` preventDefault so the selection survives, and active state comes from `queryCommandState`. Bold must render at weight ≥ 600 or Chromium's `queryCommandState('bold')` (and Ctrl+B toggling off) breaks. Right-click keeps the native menu (spellcheck, cut/copy/paste) inside the editor. Shortcuts: Mod+Shift+P pin, Mod+N new note (Mod = ⌘ on Mac, Ctrl elsewhere). The native context menu is suppressed everywhere except the editor and the title input.

## Conventions

- **Colour labels** must stay in sync in three places: `COLORS` in `store.rs` (server-side validation), the `.swatch` buttons in `index.html` and `manager.html`, and the `[data-color=...]` rules in `base.css`. Empty string = no colour; `mono` maps to `--color-paper`, so it is white in the dark theme and black in the light one (its swatch label is switched by `renderMonoName`); a `#rrggbb` value is a per-note custom colour (validated by `is_valid_color`, picked through the "Personalizada" swatch → hidden `<input type="color">`, applied as an inline `--note-color` with `data-color="custom"`); new notes start with the default colour chosen in the manager (`Store::default_color`, falling back to `DEFAULT_COLOR` = `yellow`, which is also the `Default` for `Note.color`).
- **Note model** uses `#[serde(rename_all = "camelCase", default)]`, so new fields need a `Default` value and appear camelCase in JS (`updatedAt`, `createdAt`). The file format has `version: 1`.
- **Design:** follow `docs/style.md` — near-black surfaces (Carbon `#0f1011` is the note background, also set as the native window background to avoid a white flash), Inter at weights 400–590, hairline borders. The only colour on screen is the note's label (stripe + dot); the pin button is deliberately colourless (pinned = filled white icon on a subtle grey background). Use the CSS custom properties in `styles.css` rather than raw colours.
- **CSP** (`tauri.conf.json`) is `default-src 'self'`: no CDNs, remote fonts or inline scripts. Keep all assets local.
- Rust errors returned to JS are `String`s (logged to the console, not shown), in Portuguese.
- **Strings:** add every new UI string to both `pt` and `en` in `i18n.js` (and to `tray_labels` / `welcome.rs` if it lives in Rust).
