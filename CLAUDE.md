# CLAUDE.md

Memo is a cross-platform (Windows/macOS/Linux) sticky-notes desktop app built on **Tauri 2**. Each note is its own frameless window; the headline feature is the pin button, which toggles "always on top". Code, comments, docs, config labels and commit messages are in **English** — keep new code consistent with that (only the UI is bilingual). In the UI, a note is called a **memória** (en: *memory*) — "Nova memória", "Gerenciador do Memo" / "Memo Manager"; internal names stay `note` (`notes.json`, `note-*` labels, commands). The UI is translated: Portuguese (default) and English (see *Languages* below); every new user-facing string needs both.

## Commands

```bash
npm install
npm run dev      # tauri dev — runs the app with the Rust backend in debug (also "Run in dev mode" in .vscode/launch.json)
npm run build    # tauri build — installers in src-tauri/target/release/bundle/
```

Windows installer without a local toolchain: `docker compose -f docker/compose.yml run --build --rm windows` (also the "Build Windows installer (Docker)" entry in `.vscode/launch.json`). It cross-compiles with `cargo-xwin` and outputs only the NSIS `*-setup.exe` to `dist/` (no `.msi` — WiX needs Windows). `node_modules`, `target` and caches live in Docker volumes, separate from the host's.

There are no tests, linters or JS build step. For Rust-only checks: `cargo check` / `cargo clippy` inside `src-tauri/`.

CI (`.github/workflows/build.yml`) builds installers for Windows, macOS arm64 + x64, and Linux (ubuntu-22.04). It runs only via `workflow_dispatch` (manual); run from a `v*` tag, it creates a draft GitHub release via `tauri-action`. Builds are unsigned.

## Architecture

**One window per note.** Window label is `note-{id}`; Rust derives the note id from the calling window's label (`id_of`), so commands never take an id argument — the frontend just calls `invoke('save_text', { text })` etc. and it applies to its own note. All windows load the same `index.html`; `app.js` calls `load_note` on startup to get its data.

**Default data folder / rename:** the default folder is `<OS data folder>/memo` (`default_data_dir`, `DATA_FOLDER`), *not* Tauri's `app_data_dir()` (which is named after the identifier `br.memo.notas`) — never use `app_data_dir()` for notes or config. It used to be the identifier's folder, and before that the app was called *Taxinha* (`br.taxinha.notas`). On startup `migrate_old_data` copies `notes.json` and `config.json` from the newest of those old folders (`OLD_DATA_FOLDERS`) into `memo` when neither file exists there yet (old folders are left as backups). The identifier can now change without moving the data, but WebView storage would still move.

**Rust is the source of truth.** `Store` (`store.rs`) holds all notes in a `Mutex<FileData>` and sets a `dirty` flag on change. A background thread calls `flush()` every 800 ms; it writes atomically (`notes.json.tmp` → rename). Unreadable `notes.json` is backed up as `notes.corrupted-<ms>.json` before starting fresh — never overwrite user data. `flush()` is also called explicitly on delete, quit and `RunEvent::Exit`.

**Data folder:** `notes.json` lives in the default data folder (`memo`, see below) unless the user picked another one in the manager's Configurações → Armazenamento. That choice is stored in `config.json` (`store::Config { dataDir }`), which always stays in the default data folder (`CONFIG`); `data_dir` resolves it at startup and falls back to the default for the session if the custom folder can't be created (e.g. unplugged drive). `Store.path` is a `Mutex` (always locked before `data`) so `Store::relocate(path, load_existing)` can switch files at runtime: it flushes pending changes to the old file, then either loads the destination's `notes.json` or writes the current notes there (backing up an existing file as `notes.backup-<ms>.json`). The old file is never deleted. `choose_data_dir` (native folder picker via `tauri-plugin-dialog`, called from Rust so no JS permission is needed) and `reset_data_dir` both go through `move_data_dir`, which asks with a native 3-button dialog (open those / replace with current / cancel) when the destination already has notes, and shows a native error dialog on failure. After loading another file, `reload_windows` recreates the note windows, re-applies theme/tray/title and emits `store-replaced`, on which the manager reloads its page. Dialog texts are in `storage_text` (pt/en). **Backup** (same tab): `export_notes(fileName)` writes all data with `Store::export_to` (same format as `notes.json`, trashed notes left out; the page suggests `memo-YYYY-MM-DD.json`); `import_notes` merges a picked file with `Store::import_from` — unknown ids are added, known ones replaced only if the imported `updatedAt` is newer, settings ignored — then opens/reloads (`reload()`) the windows of the changed notes and returns the count, shown in `#storageStatus`.

**Tauri commands** (`main.rs`, registered in `generate_handler!`): note windows use `get_theme`, `drag_to`, `resize_to`, `load_note`, `save_text`, `set_pinned`, `set_color`, `set_title`, `new_note`, `trash_note`, `list_groups`, `get_note_group`, `set_note_group`; group bars use `load_group`, `rename_group`, `toggle_group`, `new_note_in_group` (+ / Mod+N: a note created already in the group beside the bar, taking a closed group out first), `set_group_color`, `set_group_height`, `delete_group`; the "Gerenciador" window uses `load_manager`, `close_manager`, `bring_notes_to_front` (titlebar button; like `show_all` via `raise_notes` — notes first, group bars last so they end on top — but never creates a note), `list_groups`, `move_note_to_group`, `list_notes` (all notes, `html` stripped), `open_note`, `move_to_trash`, `restore_note`, `delete_forever`, `empty_trash`, `get_default_color`, `set_default_color`, `get_data_dir`, `choose_data_dir`, `reset_data_dir`, `export_notes`, `import_notes` — the note ones take explicit note ids. Commands that create/destroy windows are `async` on purpose — creating/destroying windows from sync commands can deadlock on Windows. When adding a command, register it in `generate_handler!`; if it needs a new window API from JS, add the permission in `capabilities/default.json`.

**Geometry** is tracked from `WindowEvent::Moved/Resized` in `track_geometry`. Position is stored in *physical* pixels, size in *logical* pixels. `TITLEBAR_H` (36px, matches `--titlebar-h` in CSS) is the minimum window height. There is no collapse feature (removed twice — don't bring it back): a titlebar double-click renames. Saved positions are only restored if the titlebar would be on a connected monitor (`is_on_screen`); Windows' `-32000` minimise coordinates are ignored. Dragging is started by the page, not `startDragging`, but follows the cursor in Rust ("Dragging and Snap" in main.rs): the titlebar captures the pointer and, past a 3 px threshold, calls `drag_start` (records the grab offset from `cursor_position()`, keeps the window always-on-top for the drag), then `drag_to` on moves (calls are chained; queued moves share one call) and `drag_end` on release; `drag_move` places the window at `cursor − grab` and applies `snapped` before `set_position`. **Snap** (like Aero Snap): with the cursor within `SNAP_EDGE` (4 logical px) of a monitor edge, `snap_zone` picks the left/right half of the work area, a quarter near a corner (top/bottom fifth, or the outer tenth of the top edge) or the whole work area (top edge), inset by `SNAP_GAP`; the hidden `snap-preview` window (`snap.html`, transparent, click-through, not focusable, created at startup by `build_snap_preview`; excluded from magnet targets, `beside` and theme backgrounds via `is_app_window`) shows it, and `drag_end` applies it, keeping the previous logical size in `Drags.restore` so the next drag restores it (cursor kept at the same relative x); a manual resize (`resize_to`) forgets it. Restore sizes are not persisted. `snapped` collects candidate corner positions per axis — the work-area edges of the monitor under the note's centre, plus the edges of every other note really on the user's screen — shown, not minimised, on that same monitor and not covered by other windows (`shows_on_screen`, per OS: Windows asks `WindowFromPoint` for a 3×3 grid of points over it (`windows-sys`); macOS reads `NSWindow.occlusionState` (`objc2-app-kit`); Linux/X11 walks the root window's stacking order for the same grid (`x11-dl`, its own Xlib connection, errors ignored meanwhile); native handles come from `raw-window-handle`; when a system can't tell, the note counts as shown) — in the same row (for x) or column (for y): side by side with a uniform `SNAP_GAP` (6 logical px) between them, or aligned — and picks the nearest one within `SNAP_DISTANCE` (16 logical px). Monitor work-area edges are inset by the same `SNAP_GAP`, so a note never sits flush against the screen edge (also in `beside`). All snapping uses the visible rect (`inner_position`/`inner_size`), not the outer one: on Windows an undecorated window has an invisible 8 px resize border on the left, right and bottom (not the top), which would leave uneven gaps; `drag_to` converts between the two with the inner−outer offset. The native drag loop can't do this because the OS owns the window until the button is released. Resizing works the same way: windows are built with `resizable(false)`, `chrome.js` adds invisible handles on the 4 edges and 4 corners (plus the visible bottom-right grip) and sends the requested visible rect to `resize_to`, which snaps only the moving edges using the same `SnapTargets` (per-edge candidate lines shared with `snapped`) and enforces `MIN_W`/`MANAGER_MIN_W` × `TITLEBAR_H`. A note created with `+` is placed by `beside`: next to its parent with the same visible `SNAP_GAP` (computed on inner rects, assuming the new window has the parent's invisible borders), right side first, else left, within the monitor work area; if another visible note already sits on that spot, it steps down by `COLLAPSED_H + 8` until free, so repeated `+` clicks cascade instead of stacking.

**Groups** ("Groups" in main.rs, `group.html`/`group.js`): a `Group` (`FileData.groups`: id, name, outer x/y, logical width, `open`) is a compact bar window labelled `group-{id}` (`open_group_window`, height `TITLEBAR_H`, with its own pin — `Group.pinned`, saved through the shared `set_pinned`, Mod+Shift+P — and colour — `Group.color`, same labels as notes, picked by clicking the folder icon, which is drawn in the group's colour and plays the part of a note's colour dot (`#colorBtn`, `set_group_color`); while the picker is open the window grows with `set_group_height` (not saved) and shrinks back; the colour also tints the note footer's folder and the manager's group chip — only e/w resize handles via `MemoChrome.attach({ resizeEdges })`, no Snap); notes point to it with `Note.group_id` (`normalize` clears links to missing groups). The arrow button (`#toggleBtn`, up = put away, down = take out) → `toggle_group`: `take_out` builds the members' windows hidden at their saved place, moves them to the bar and slides them there (`slide`, ~140 ms ease-out on a worker thread), `put_in` slides open members into the bar and destroys them; the `Sliding` set makes `track_geometry` ignore those moves so notes keep their places (cleared on `Destroyed`, or 150 ms after a slide-out). Double-click on the bar renames (`rename_group`, `GROUP_NAME_MAX`); ✕ (twice when not empty) or middle click → `delete_group`: members go through `trash()`, then `remove_group`. A note joins by being dropped on a bar (`drag_move` → `group_under`, broadcasting `drop-hover` `[groupId, on]`; `drag_end` → `join_group`, sliding back to the drag's start if the group is open, into the bar if closed), from its footer picker (`set_note_group`) or the manager's row `<select>` (`move_note_to_group`); both go through `assign_group` (`""` = leave, `"new"` = `create_group`, unnamed, placed with `beside`). Startup opens every group bar and only `Store::visible()` notes (not inside a closed group); `open_note` on a note of a closed group takes the whole group out; `restore_note` doesn't open a note whose group is closed. Changes emit `groups-changed` (group bars, note footers and the manager reload on it). The note footer's bottom-left button (`#footBtn`) always shows the note's group with a folder icon ("Sem grupo" / "No group" without one; the edit date is no longer shown) and opens `#groupMenu`. Groups start unnamed, like notes (`create_group` sets no name; `rename_group` accepts an empty one); an unnamed group reads "Sem título" / "Untitled" (`untitled`, the same as an untitled note) on its bar, in the footer, the picker and the manager, and its native window title is "Memo" (`group_title`).

**Trash:** the ✕ button / middle click (`trash_note`) and the manager (`move_to_trash`) both go through `trash()`, which sets `trashedAt` and destroys the window (a note with no text and no title is removed outright). Only notes with `trashedAt == None` (`Store::active`) are opened at startup. Notes older than `TRASH_TTL_MS` (30 days) are purged on load and hourly by the saver thread. Permanent deletion only happens from the trash (manager) or by that purge.

**Embedded editor:** `index.html?defaults` runs the same note page in *embedded* mode (`EMBED` in app.js, `html.embedded` in styles.css: no titlebar, statusbar, colour stripe or window shortcuts; Tauri API taken from `window.parent` when inside an iframe). The manager's Configuração uses it in an `<iframe id="defaultTextFrame">` to edit the new-note default text with the exact note editor; it loads `get_new_note_defaults` → `(title, text, html)` and saves with `set_default_content(text, html)`. The title is saved separately (`set_default_title`). `Store::create` copies `default_title`/`default_text`/`default_html` into new notes.

**Manager ("Gerenciador" window):** label `manager` (`MANAGER`), page `manager.html`. It behaves like a note — frameless, same titlebar (pin, +, ✕) plus a "bring all memories to the front" button (`#raiseBtn`) and a "new group" button (`#newGroupBtn` → `new_group`: an empty, unnamed group beside the manager) before the +, drag with snapping and middle-click close via `chrome.js`, resize grip, its position/size/pinned persisted in `FileData.manager` (`ManagerState`) — but has a fixed "Gerenciador" title and no editor; its colour control is a manager icon drawn in its colour (`#mgrColorBtn`, same swatch popover; `ManagerState.color`, default yellow, `set_manager_color`); its titlebar has no double-click action (its title is fixed). `set_pinned`/`track_geometry` branch on `is_note` to update the manager state instead of a note; ✕/middle click call `close_manager` (no trash). Notes snap to it and `+` from it opens a note beside it. Opened by `open_manager` at startup / relaunch and from the tray item "Gerenciador do Memo" — notes have no button for it. The tray no longer manages notes. Every change to the note list emits `notes-changed` (`notify`), and the manager reloads `list_notes` on it (debounced). It also sets the default colour for new notes (`FileData.default_color`, used by `Store::create`). Code that iterates windows must tell them apart with `is_note` / `is_group` / `is_app_window` (the latter excludes the Snap preview). The tray menu has only static items (Nova nota, Mostrar todas as notas, separator, Gerenciador do Memo, separator, Sair do Memo); the theme lives in the manager's "Configurações" tab and the welcome-note button (`show_welcome`) in its "Ajuda" tab. The manager has four tabs (equal-width `.tab` buttons; when a tab can't fit its label — small window, zoom, language — `fitTabs` sets `.mgr-head.compact` and one `#viewSelect` replaces them with the same sections and counts; likewise `fitSettings` sizes the settings label column to the widest label (`--label-w`; labels never wrap) and stacks every label above its control (`.settings.stacked`) only once some control no longer fits beside its label) — Memórias and Lixeira (both with the search box and sort select), Configurações (appearance, new-note defaults, storage/backup, quit) and Ajuda (no list, no search for the last two). Ajuda is a how-to guide: its groups are data in `i18n.js` (`HELP`, `MemoI18n.help()`, pt/en), rendered by `renderHelp` in manager.js; in each "how" text `{{…}}` marks a key or something to type, shown as `<kbd>` through `keys()` (Mod → Ctrl/⌘). Items are `[topic, how, demo?]`: `demo` is an optional static HTML example (`demoBox`) drawn like the real thing — editor markup (`b`/`i`/`u`, `.hl`, `.sz-2`/`.sz-5`, `.check`, `.bullet`, `code`, `pre.code[data-lang]` highlighted with Prism, which manager.html also loads), `<i data-icon="pin|pin-on|plus|close|search|sort">` for chrome icons and `.demo-*` mock-ups styled in manager.css; add one whenever a feature can be shown. Prism token colours live in base.css for both pages. Keep the guide in sync when features or shortcuts change. New-group defaults (Configurações → "Padrão dos grupos": colour — `None` = `DEFAULT_COLOR` yellow, as for notes — and title, empty = unnamed) live in `FileData.default_group_color` / `default_group_title` (`get_group_defaults`, `set_default_group_color`, `set_default_group_title`) and are applied by `Store::create_group`. New-note defaults live in `FileData` (`default_color`, `default_title`, `default_text` — plain text, `[ ] ` lines become checklist items via `fromPlain` since the new note's `html` is empty) and are applied in `Store::create`; `trash()` deletes outright a note still equal to those defaults (`Store::is_pristine`).

**Zoom:** a global zoom of every window's content (`FileData.zoom`, `ZOOM_MIN`..`ZOOM_MAX` by `ZOOM_STEP`, 1.0 = 100%), changed in Configurações → Aparência (− / % / + / reset) or with Mod + / Mod − / Mod 0 / Mod + wheel in any window (`MemoZoom` in chrome.js, also attached in the embedded editor) → `change_zoom(step)` (0 = reset) → `set_zoom` on every app window and `zoom-changed`; new windows get it when built. Group bars are a titlebar tall, so their height is `TITLEBAR_H × zoom` (and `set_group_height` scales the CSS height it gets); `resize_to`'s minimum height scales too.

**Theme:** app-wide setting stored in `notes.json` (`FileData.theme`: `system` | `light` | `dark`, empty = system), chosen in the manager's segmented switch (`change_theme` command). `set_theme` saves it, updates every window's native background (`apply_background`: `PAPER` or `CARBON`; "system" uses `window.theme()`, re-applied on `WindowEvent::ThemeChanged`) and emits `theme-changed`; `app.js` reads it with `get_theme` and sets `<html data-theme>` (no attribute = follow the OS through `prefers-color-scheme`). In CSS the light theme redefines the same grey tokens (`--color-carbon`, `--color-mist`, …) plus the `--overlay-*`, `--selection` and `--shadow-popover` tokens — never use raw white/black overlays, use those tokens so both themes work.

**Startup:** the Gerenciador opens on every launch (`setup`), on relaunch through the single-instance plugin and on macOS Dock reopen, together with the notes that were open. **First run:** when `Store::is_first_run()` (no notes and `next_seq <= 1`, i.e. a fresh `notes.json`), `setup` creates the welcome note from `welcome.rs` instead of an empty one, placed beside the Gerenciador (`open_welcome(app, pos)` with `beside`). The "Abrir a memória de boas-vindas" button in the manager's Ajuda tab (`show_welcome`) reopens it through the same `open_welcome`, which focuses an untouched copy (same title and HTML) if one is open instead of duplicating it. Only the first-run welcome note goes to the trash when closed: copies opened from Ajuda get `Note.welcome_copy = true` and `trash()` deletes them outright (even if edited or ticked). Its `HTML` must only use tags the `sanitize` whitelist keeps, and `TEXT` must equal what `toPlain` produces from that HTML.

**Languages:** `FileData.language` is `system` | `pt-BR` | `en` (empty = system); `Store::effective_language()` resolves it to `"pt"` or `"en"` (system: `sys-locale`, Portuguese for any `pt*` locale, English otherwise). Pages call `get_language` → `(setting, effective)` and `MemoI18n.set(effective)`; the manager's Configuração has a language list (`<select id="languageSelect">`, `change_language`), and `set_language` emits `language-changed` (effective lang) to every window, rebuilds the tray (`refresh_tray`, main thread) and retitles the manager. In HTML, static text uses `data-i18n="key"` and `data-i18n-attr="attr=key,…"`; JS uses `t('key', vars)`. Rust-side strings (tray labels, manager window title, welcome note) are chosen with the effective language (`tray_labels`, `manager_title`, `welcome::for_lang`). Note content and new-note defaults are never translated.

**Tray clicks:** a left click on the tray icon opens the manager (`open_manager`; Linux trays send no clicks — the menu has the item).

**Lifecycle:** single-instance plugin (relaunch → `show_all`). Each note window appears in the taskbar (grouped under the app icon); on macOS the app has a Dock icon and `RunEvent::Reopen` → `show_all`. Closing the last window doesn't quit (`prevent_exit` when no exit code); with no notes open the app lives only in the tray, and only "Sair do Memo" (tray menu, or `quit_app` in the manager's Configurações tab) exits. On Linux under Wayland, `GDK_BACKEND=x11` is forced (unless already set) so always-on-top works through XWayland.

**Frontend (`app.js`)**: a single IIFE. Text saves are debounced 250 ms and flushed on blur/window blur/beforeunload. Pin toggling is optimistic and reverts on error. Titlebar layout: pin on the far left, colour dot (`#colorBtn`, opens the swatch popover `#colorMenu`), name, then new / close on the right (hidden, and taking no room, unless the window is focused or hovered, so the name can use the full width). It handles drag (custom, see below), middle-click close (`auxclick` → `closeNote`, same as ✕) and double-click rename (inline `#titleInput` → `set_title`, max 80 chars). The note name (or first line) is mirrored to the native window title (`setTitle`) for the taskbar. The bottom-right grip calls `startResizeDragging`.

**Editor:** `#editor` is a `contenteditable` div; each line is a `<div>`, formatting is `<b>`/`<i>`/`<u>` (`styleWithCSS` off), highlight as `<span style="background-color: rgb(255, 230, 0)">` (only that exact sentinel counts — Chromium creates other background spans) from `execCommand('hiliteColor')` (a sentinel colour; CSS paints it with the theme's `--highlight` via `!important`, `sanitize` keeps only spans with a non-transparent background, removal sets `transparent`; Mod+Shift+H and the marker button in the format bar) plus text size as `<font size="2|3|5">` from `execCommand('fontSize')` (`SIZES` in app.js; real px sizes in the `.editor font[size]` CSS rules — keep the two in sync), and a checklist item is `<div class="check">` (checked: `check done`, box drawn in CSS `::before`); inline code is `<code>` (typing `` `x` `` → `expandInlineCode`, or Mod+E / `</>` → `toggleCode`; inserted straight into the DOM with a trailing U+200B so the caret leaves the code — Chromium's `insertHTML` would copy inline styles; U+200B is stripped from plain text); a code block is `<pre class="code" data-lang>` holding only text and `<br>` (```` ```lang ```` + Enter → `openCodeBlock`; inside it Enter = line break, Tab = two spaces, Enter on an empty last line leaves, list/inline conversions are disabled; `preText` reads it; `data-lang` is normalised by `codeLang` — aliases like `js`/`py`/`sh` map to the `CODE_LANGS` values, unknown names are kept as typed). Syntax highlighting is presentation only: the pre's own text is `color: transparent`, and `renderCode` (run on every content change, scroll, resize and language change) lays one item per block in `#codeLayer` — a sibling of the editor inside `.body`, so nothing of it is saved — with Prism's highlighted copy (`src/vendor/prism.js`, vendored core + 20 languages, loaded `data-manual`) positioned over the block and mirroring its computed font/padding/wrapping, plus, shown while the mouse is over the block, a `<select class="code-lang">` in the top-left corner that sets `data-lang` (`setCodeLang`) and a copy button (`.code-copy`, top-right → `copyCode`: the block's `preText` to the clipboard through a synchronous `copy` event — the editor keeps focus — with `navigator.clipboard` as fallback; a check for 1.5 s). Token CSS uses colours only (`--code-*` in base.css, both themes): bold/italic would change glyph widths and misalign the copy; in plain text they are `` `x` `` and ```` ```lang … ``` ```` fences (`fromPlain` parses both); a bulleted item is `<div class="bullet">` (typing `- ` at line start, `expandBullet`). Both can carry `data-level` 1–4 (Tab / Shift+Tab via `setLevel`; Enter on an empty item or Backspace at its start outdents first, then leaves the list); in plain text each level is two leading spaces before `[ ] `/`[x] `/`- ` (`listPrefix`, `LIST_RE`). `syncCheckSizes` (run on load and every change) gives an item whose text is all in one `<font size>` a `data-size` so the line itself takes that size (box and strike-through centred); mixed-size items get an inline `--check-mid` with the measured first-line centre. Both are presentation only — `sanitize` drops them and they are recomputed. The note stores both `html` (the editor's `innerHTML`, re-sanitised to that whitelist on load by `sanitize`) and `text` (plain text via `toPlain`, items as `[ ] ` / `[x] `; `[]` is also accepted by `LIST_RE`/`plain`, and `set_new_note_defaults` normalises it to `[ ]`) — Rust only reads `text` (`is_blank`), and notes with empty `html` are rebuilt from `text` (`fromPlain`). `save_text` takes both. Typing `[]` at line start turns the line into an item, clicking the box toggles it, Enter on an item continues the list (the browser clones the block; `done` is cleared), Enter on an empty item or Backspace at its start leaves the list. Paste is always plain text. **Undo is the editor's own** ("undo" section in app.js): many edits change the DOM directly (inline code, code blocks, checklist boxes, list levels), which Chromium's undo stack never sees, so `onContentChanged(typing)` records a snapshot (HTML + selection as child-index paths) after every change (`recordHistory`; typing within `TYPING_MS` merges into one step, a paste never does), `selectionchange` keeps the current step's caret up to date, and Mod+Z, Mod+Shift+Z / Mod+Y and `beforeinput` historyUndo/historyRedo call `restoreHistory`. Auto-conversions (`` `x` ``, `[]`, `- `) record the typed text first, so undo brings the characters back; their internal execCommand edits are ignored by the `converting` guard. Any new DOM-changing edit must end in `onContentChanged()` so it gets an undo step. Formatting: Mod+B/I/U, Mod+Shift+> / Mod+Shift+< (text size, matched by `e.code` Period/Comma), or the floating `#formatBar` (N / I / S + three "A" size buttons) shown above a non-empty selection — hidden while the mouse drags a selection, repositioned on `selectionchange`/scroll/resize, buttons use `mousedown` preventDefault so the selection survives, and active state comes from `queryCommandState`. Bold must render at weight ≥ 600 or Chromium's `queryCommandState('bold')` (and Ctrl+B toggling off) breaks. Right-click keeps the native menu (spellcheck, cut/copy/paste) inside the editor. Shortcuts: Mod+Shift+P pin, Mod+N new note (Mod = ⌘ on Mac, Ctrl elsewhere). The native context menu is suppressed everywhere except the editor and the title input.

## Conventions

- **Every feature works on Windows, macOS and Linux.** Don't ship a behaviour on one system only: when something needs native APIs, implement it for all three (gate with `#[cfg(windows)]` / `#[cfg(target_os = "macos")]` / `#[cfg(target_os = "linux")]`, using crates already in the dependency tree where possible) and keep a sensible fallback elsewhere. Remember Linux runs under X11 (XWayland is forced) and macOS needs `macOSPrivateApi` (on, with the `macos-private-api` tauri feature) for transparent windows such as the Snap preview. This machine is Windows: check the other targets before saying they work — `cargo check --target aarch64-apple-darwin` fails on a C build script, so compile macOS-only code in an isolated crate with the same versions; for Linux run `cargo check`/`clippy` in Docker (`rust:1-bookworm` with `libwebkit2gtk-4.1-dev libayatana-appindicator3-dev librsvg2-dev`).
- **Consistent usability across components — always.** Notes, group bars and the manager are the same kind of window and must behave the same way wherever they share a concept. When you add or change an interaction in one of them, apply it to every component where it makes sense in the same change (or say explicitly why not), and never introduce a second way of doing what an existing control already does. Today that means:
  - **Titlebar:** same frame and order — pin on the far left; colour control next to it, opening the same swatch popover (a note's `.color-btn` dot; a group's folder icon and the manager's manager icon, drawn in their colour); then the name; action buttons on the right (`+`, ✕…), hidden and taking no room unless the window is focused or hovered. Same icons (SVG paths) for the same action everywhere, including the Help demos.
  - **Gestures and shortcuts:** drag with magnet/Snap and the resize handles come from `chrome.js` for every window; double-click on the titlebar renames (notes and groups; the manager's title is fixed); a group's arrow button takes its notes out / puts them in; middle click = ✕; Mod+Shift+P pins; Mod+N creates a note (inside the group when on a group bar); Esc closes popovers and cancels editing; Enter confirms.
  - **Same rules, same outcomes:** names start empty and show "Sem título"/"Untitled" greyed out until named; colours use the same labels, swatches and custom picker (`COLORS`, `is_valid_color`); deleting asks for a second click when data would go to the trash; confirmations, tooltips (with their shortcut), placeholders and wording reuse the existing `i18n.js` keys instead of new near-duplicates.
  - **Everywhere it shows:** a feature visible in one place appears consistently wherever the same object shows up (e.g. a group's name and colour in its bar, the notes' footer, the footer picker and the manager list — where each row always shows the group's folder icon in its colour, the group `<select>` and the trash button).
  - Keep the Help tab (`HELP` in `i18n.js`, with demos), the welcome note (`welcome.rs`), README and this file in step with any such change.
- **Colour labels** must stay in sync in three places: `COLORS` in `store.rs` (server-side validation), the `.swatch` buttons in `index.html`, `group.html` and `manager.html`, and the `[data-color=...]` rules in `base.css`. `lavender` is legacy: still valid and rendered (old notes/groups keep it) but no longer offered in the pickers. Empty string = no colour; `mono` maps to `--color-paper`, so it is white in the dark theme and black in the light one (its swatch label is switched by `renderMonoName`); a `#rrggbb` value is a per-note custom colour (validated by `is_valid_color`, picked through the "Personalizada" swatch → hidden `<input type="color">`, applied as an inline `--note-color` with `data-color="custom"`); new notes start with the default colour chosen in the manager (`Store::default_color`, falling back to `DEFAULT_COLOR` = `yellow`, which is also the `Default` for `Note.color`).
- **Note model** uses `#[serde(rename_all = "camelCase", default)]`, so new fields need a `Default` value and appear camelCase in JS (`updatedAt`, `createdAt`). The file format has `version: 1`.
- **Design:** follow `docs/style.md` — near-black surfaces (Carbon `#0f1011` is the note background, also set as the native window background to avoid a white flash), the system UI font (`--font-ui`: Segoe UI / SF Pro / distro default — no bundled font files; use weights 400, 500 for titles/labels and 700 for bold text in the editor (`<b>`, in `--color-paper`); avoid other intermediate weights, they snap to semibold), hairline borders. The only colour on screen is the note's label (stripe + dot); the pin button is deliberately colourless (pinned = filled white icon on a subtle grey background). Use the CSS custom properties in `styles.css` rather than raw colours.
- **CSP** (`tauri.conf.json`) is `default-src 'self'`: no CDNs, remote fonts or inline scripts. Keep all assets local.
- Rust errors returned to JS are `String`s (logged to the console, not shown), in English.
- **Strings:** add every new UI string to both `pt` and `en` in `i18n.js` (and to `tray_labels` / `welcome.rs` if it lives in Rust).
