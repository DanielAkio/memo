# Windows, dragging, Snap, lifecycle

Code: `src-tauri/src/windows.rs` (building, placing, geometry, magnet targets) and `drag.rs` (dragging, Snap, resizing), `beside` in `notes.rs`, the tray in `tray.rs` (see `memo-code-map`); `src/lib/chrome.js`, `src/components/titlebar.js` (the titlebar every window shares), `src/windows/snap/snap.html`.

## Geometry

Tracked from `WindowEvent::Moved/Resized` in `track_geometry` (`Kind::of`: a note, group or board, or `None` = the manager's `ManagerState`). Position is stored in **desktop units** (`desk.rs`), size in **logical** pixels. Desktop units are the one space where the cursor, windows and monitors compare: physical pixels on Windows/Linux; on macOS points × the main monitor's scale, because Tauri's "physical" values there use a different scale per object (cursor: main monitor's; window: its own; monitor: its own), so a drag on a monitor with another scale ran at the wrong speed. Anything that compares or sets positions (drag, magnet, Snap, resize, `beside`, `is_on_screen`, group slides, saved positions) goes through `desk::*`; on a single monitor the values equal Tauri's. `TITLEBAR_H` (36 px, = `--titlebar-h` in CSS) is the minimum window height. Saved positions are restored only if the titlebar would be on a connected monitor (`is_on_screen`); Windows' `-32000` minimise coordinates are ignored. **Mixed-scale monitors (Windows):** a window's `scale_factor()` can lag behind the monitor it is on (a window built on the main monitor and placed elsewhere while hidden keeps the main monitor's scale), so logical↔physical conversions use `scale_of` (the scale of `current_monitor()`) and `set_logical_size`; restored notes, group bars and the manager are re-sized for the monitor they land on. The drag's grab offset is kept in logical pixels so the cursor stays on the same spot when the window changes size crossing monitors. No collapse feature (removed twice): a titlebar double-click renames; folding to the titlebar happens only by resizing (titlebar magnet, below).

All snapping uses the **visible** rect (`inner_position`/`inner_size`), not the outer one: on Windows an undecorated window has an invisible 8 px resize border on left, right and bottom (not top). `drag_to` converts between the two with the inner−outer offset.

## Dragging

Started by the page, not `startDragging` (the OS would own the window until release, so no magnet/Snap). The titlebar captures the pointer and, past a 3 px threshold, calls `drag_start` (records the grab offset from `cursor_position()`, keeps the window always-on-top during the drag; `drag_end` puts back the window's own pin through `pinned()`, which must know every window kind — note, group, board, manager — or an unpinned window stays above the others), then `drag_to` on moves (calls are chained; queued moves share one call) and `drag_end` on release. `drag_move` places the window at `cursor − grab` and applies `snapped` before `set_position`.

Note, manager and group windows are built with `accept_first_mouse(true)`: on macOS a click on an inactive window otherwise only focuses it, so dragging (or any button) needed a second click. It only affects WKWebView; Windows and Linux already deliver the first click.

**Magnet (`snapped`)** collects candidate positions per axis — work-area edges of the monitor under the window's centre, plus edges of every other note really on screen (shown, not minimised, same monitor, not covered: `shows_on_screen`) in the same row (x) or column (y), either side by side with a uniform `SNAP_GAP` (6 logical px) or aligned — and picks the nearest within `SNAP_DISTANCE` (16 logical px). The magnet can be turned off (Settings → Aplicativo → "Ímã das janelas", or the tray check item; `FileData.magnet_off`, `Store::magnet`, `get_magnet` / `set_magnet` → `toggle_magnet`, emits `magnet-changed`): `SnapTargets::new` then returns no targets, so neither dragging nor resizing pulls, and the titlebar magnet is off too. Snap (below) still works. Work-area edges are inset by `SNAP_GAP` so nothing sits flush against the screen edge (also in `beside`).

`shows_on_screen` per OS: Windows asks `WindowFromPoint` for a 3×3 grid of points (`windows-sys`); macOS reads `NSWindow.occlusionState` (`objc2-app-kit`); Linux/X11 walks the root window's stacking order for the same grid (`x11-dl`, own Xlib connection, errors ignored); native handles via `raw-window-handle`; when a system can't tell, the window counts as shown.

**Snap** (like Aero Snap): with the cursor within `SNAP_EDGE` (4 logical px) of a monitor edge, `snap_zone` picks the left/right half of the work area, a quarter near a corner (top/bottom fifth, or the outer tenth of the top edge) or the whole work area (top edge), inset by `SNAP_GAP`. The hidden `snap-preview` window (`snap.html`; transparent, click-through, not focusable, built at startup by `build_snap_preview`; excluded via `is_app_window`) shows it; `drag_end` applies it and keeps the previous logical size in `Drags.restore`, so the next drag restores it (cursor kept at the same relative x). A manual resize forgets it; restore sizes are not persisted. Group bars don't Snap.

## Resizing

Windows are built with `resizable(false)`. `chrome.js` adds invisible handles on the 4 edges and 4 corners (plus the visible bottom-right grip; group bars get only e/w via `resizeEdges`) and calls `resize_start` on pointerdown (Rust records the cursor and the visible rect) and `resize_to(edges)` on moves (chained like `drag_to`), which follows the cursor in physical pixels (the page's screen coordinates jump between monitors with different scales) and snaps only the moving edges with the same `SnapTargets` and enforces `MIN_W` / `MANAGER_MIN_W` × `TITLEBAR_H` (scaled by zoom). **Titlebar magnet:** when a resize of a note's top or bottom edge leaves less than `TITLEBAR_SNAP` (40 logical px) of text, the note snaps down to `TITLEBAR_H`, folding the text into the titlebar; pulling the edge past that distance opens it again. It must not depend on the current size (an earlier "only while shrinking" check made it bounce open on the next pointer move). This is only a resize snap, not a collapse state (nothing is stored but the height).

## New notes: `beside`

A note created with `+` (or from the manager, or the welcome note) is placed by `beside`: next to its parent with the same visible `SNAP_GAP` (inner rects, assuming the new window has the parent's invisible borders), right side first, else left, within the work area; if a visible note already sits there it steps down by `TITLEBAR_H + 8` until free, so repeated `+` cascades.

## Close vs trash

✕ / middle click never trash. On a note, `close_window` (→ `close_note_by_id`; groups and boards have their own `_by_id`) sets `Note.hidden` and destroys the window; the note stays among the current ones (dimmed `.is-closed` row in the manager) and `open_note` reopens it. A pristine note (`is_pristine`) or a welcome copy is deleted outright through `trash()`. Only the manager's trash buttons trash: `move_to_trash` → `trash()` sets `trashedAt` and destroys the window (a note with no text and no title is removed outright). `take_out`, `leave_group` and `restore_*` clear `hidden`.

## Startup, first run, lifecycle

- `setup` opens the manager plus `Store::visible()` notes and every active group bar; the same on relaunch (single-instance plugin → `show_all`) and macOS Dock reopen (`RunEvent::Reopen` → `show_all`).
- Started with `--autostart` (`AUTOSTART_ARG`): reopens notes but not the manager (except on first run) and creates no empty note.
- **First run** (`Store::is_first_run()`): creates the welcome note from `welcome.rs`, placed beside the manager (`open_welcome(app, pos)` → `beside`). The Help tab's button (`show_welcome`) reuses `open_welcome`, focusing an untouched open copy instead of duplicating. Only the first-run welcome note goes to the trash when trashed; copies get `Note.welcome_copy = true` and `trash()` deletes them outright. `welcome.rs` HTML must only use tags `sanitize` keeps, and its `TEXT` must equal what `toPlain` produces from that HTML.
- `show_all` / `bring_notes_to_front` go through `raise_notes`: notes first, group bars last so they end on top (`bring_notes_to_front` never creates a note).
- Closing the last window doesn't quit (`prevent_exit` when there's no exit code); the app then lives in the tray. Only "Sair do Memo" (tray, or `quit_app` in the manager) exits.
- Each note window shows in the taskbar (grouped under the app icon); macOS has a Dock icon. On Linux under Wayland, `GDK_BACKEND=x11` is forced (unless set) so always-on-top works.
- **Tray:** `build_tray_menu` / `on_tray_menu`: Nova memória, Novo grupo, Mostrar todas as memórias | Gerenciador do Memo, Lixeira, Configurações, Ajuda | Tema ▸, Idioma ▸ (check items), Iniciar com o sistema (check), Ímã das janelas (check, `toggle_magnet`), Controle por IA (MCP) (check, `toggle_ai_control`, emits `ai-control-changed`), Sincronizar agora (only with a Google account connected) | Procurar atualizações, or "Atualizar para a versão X" once `updater.rs` found one (both open Settings scrolled to the version row, scope `update`, and check / install there) | "Memo x.y.z" (disabled, the running version from `package_info()`), Sair do Memo. Labels from `tray_labels` (pt/en). The menu is rebuilt by `refresh_tray` whenever a label or check changes (language, theme, autostart, cloud account, store replaced), so call it from any new setter the menu shows. Lixeira/Configurações/Ajuda go through `open_manager_view`: an open manager gets `manager-view`, a new one picks the tab up with `take_manager_view`. The tray's autostart toggle emits `autostart-changed` for the manager's switch. Left click opens the manager (`open_manager`; Linux trays send no clicks). Every new feature that makes sense as a command without a window goes in this menu too.
- **Titlebar menu:** the "…" button (`#moreBtn`) and a right click anywhere on a titlebar (notes, group bars, manager) open a native menu (`MemoChrome.titleMenu` → `show_title_menu`, `popup_menu` / `popup_menu_at`, so a small or collapsed window never cuts it): the window's own commands from JS (`[{ label, run, checked? }]`, null = separator) on top, then `app_menu_items(.., full: false)`: only new memory / group / board, "Import shared item" (while a link's item is offered, in Memo Web too), the manager and a newer version, with ids prefixed `win:<label>:` (the tray keeps the full list: settings, theme, language…). Own commands never repeat an always-visible button (no "Close"). Clicks reach `on_tray_menu` → `on_title_menu`: `own:<i>` goes back to the window as `title-menu`, "new"/"new-group" open beside the window (`beside`), the rest runs as from the tray. `apply_background` also sets the window's native theme so the menu follows the app's theme. Keep titlebars to the most used buttons (pin, colour, name, then share link `#shareBtn` (far left of the actions; notes, boards, group bars; wired by `TitleBar` → `MemoShare.copy()`; hidden until the pointer is over the titlebar, `base.css`, except on touch screens) / group toggle / +, …, ✕); anything else goes in the menu. A group bar's minimum width (`GROUP_MIN_W` = 210, same in web.js) fits all of them.
- Window titles: a note mirrors its name (or first line) to the native title for the taskbar; groups and boards use `window_title` ("Memo" when unnamed); the manager uses `manager_title`.

## Stacking

The last window clicked is on top; only pinned windows (notes, group bars, boards, the manager) stay above it. On the desktop the OS does this through always-on-top (`set_pinned`, and `pinned()` after a drag). In Memo Web (`site/web.js`) the workspace does it with two z-index layers: `zNormal` for unpinned windows and `zPinned` for pinned ones; `openWindow` takes the window's own `pinned`, `raiseWindow` runs on every pointerdown in a frame, and `set_pinned` / `unpinFromPip` must find the right object for each window kind (`n || g || b || data.manager`). Tested in test-ui ("the last clicked window stays on top"). Pinning in Memo Web also floats the window over other apps: Document Picture-in-Picture (`openPipForWindow`, the frame moves into the PiP window) on desktop browsers; on phones (`isMobile`) and browsers without it, a memory floats read-only through a video's PiP (`openVideoPip`: `drawNoteCard` paints it on a canvas streamed into a hidden `<video>`, redrawn on every `notifyNotes`; leaving the PiP unpins it, as closing the Document PiP does).
